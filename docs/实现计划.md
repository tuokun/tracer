## 阶段一：Rust 监听核心（详）

> ✅ **已完成并验证（2026-07-04）**：S1–S6 全部落地，S7 运行关卡通过——连续运行 30+ 分钟、扛过一次真实睡眠/唤醒、`tracer.exe` 内存 <5MB（debug）、各探针（窗口/UWP/WASAPI/idle/电源）实测正确。详见各步骤的 `✅ 已验证`。

### 目标

把"感知层"做对：能准确知道**当前前台是谁（含 UWP 真身）、是否有音频、用户是否空闲、系统是否挂起/唤醒**。本阶段**不写库**——事件经 channel 进 owner task 后只做结构化日志（`println`/`tracing`），落库留到阶段二。

### 模块划分 & 文件结构

```
src-tauri/src/
├── main.rs              # 入口：起 tokio runtime、拉起各子模块
├── core/
│   ├── mod.rs           # 模块导出
│   ├── event.rs         # 事件类型 + mpsc channel（Q4 脊梁）
│   ├── tracker.rs       # SetWinEventHook + 消息循环线程（前台切换）
│   ├── process.rs       # HWND → PID → 进程名/路径；UWP 真身提取
│   ├── audio.rs         # WASAPI 音频峰值探测
│   ├── idle.rs          # GetLastInputInfo 空闲探测
│   ├── power.rs         # WM_POWERBROADCAST 挂起/唤醒
│   └── owner.rs         # owner task（阶段一：日志；阶段二：落库）
```

> **线程模型**（见 `方案评审记录.md` 一·6）：hook 线程只解析窗口、把事件丢进 channel；owner task 是唯一写者。阶段一先把这个骨架立起来，避免阶段二再回填。

### Cargo 依赖（阶段一）

```toml

    "Win32_UI_Input_KeyboardAndMouse",   # GetLastInputInfo / LASTINPUTINFO

    "Win32_System_SystemInformation",    # GetTickCount64

    "Win32_System_LibraryLoader",        # GetModuleHandleW（注册窗口类）
    "Win32_Media_Audio",                 # IMMDeviceEnumerator / GetDefaultAudioEndpoint

] }
tracing = "0.1"
```

### 实现步骤

#### S1 · Win Event Hook + 消息循环线程

- 起一个**专用 OS 线程**，在其中调用 `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, ...)`，然后跑 `GetMessage` 循环派发。
- 回调里**只**取 `HWND`，暂不解析，先 `tracing::info!("foreground hwnd={:?}", hwnd)`。
- ⚠️ `SetWinEventHook` 的回调运行在"调用了它并跑 `GetMessage` 的那个线程"上——这就是 hook 线程；它不能阻塞、不能持锁。

**✅ 验证**：切换几个窗口，日志稳定打印变化的 `hwnd`，无崩溃。

#### S2 · 进程解析（HWND → PID → 名/路径）

- `GetWindowThreadProcessId(hwnd) → pid`。
- `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, pid) → handle`。
- `QueryFullProcessImageNameW(handle) → 绝对路径`，从中取 `process_name`。
- 失败路径（权限不足/已退出）要降级处理，不能 panic。

**✅ 验证**：切到 Chrome/资源管理器等，日志打印的 `process_name`、路径与任务管理器一致。

#### S3 · UWP 真实进程提取

- 当 `process_name == "ApplicationFrameHost.exe"` 时，`EnumChildWindows` 遍历子窗口，取子窗口 PID，得到真实业务进程（如 `Microsoft.Windows.Photos.exe`）。
- ⚠️ UWP 启动瞬间子窗口可能还没出现，需要**重试/短暂等待**或忽略本次、等下次事件。

**✅ 验证**：打开"设置""照片"等 UWP，日志打印的是真实进程而非 `ApplicationFrameHost`。

#### S4 · WASAPI 音频峰值探测

- 封装一个 `audio::is_playing() -> bool`：`CoInitializeEx`（线程内）→ `IMMDeviceEnumerator` → 默认渲染设备 → 激活 `IAudioMeterInformation` → `GetPeakValue()`，峰值 > `1E-08` 视为播放。
- ⚠️ COM 需在线程内初始化；`IAudioMeterInformation` 句柄复用要注意释放。

**✅ 验证**：播放任意音频时 `is_playing()==true`，停止后变 `false`。

#### S5 · 事件 channel + owner task 骨架

- `event.rs` 定义事件枚举：`ForegroundChanged { pid, name, path }`（后续阶段会扩 `FlushTick`/`PowerSuspend`/`PowerResume`）。
- `tokio::sync::mpsc::channel`，hook 线程 `tx.send(...)`，owner task `rx.recv()` 后结构化打印。
- owner task 是**唯一**消费方（为阶段二的"唯一写者"铺路）。

**✅ 验证**：前台切换事件经 channel 流到 owner task，owner 打印完整 `{pid, name, path}`；hook 线程与 owner task 分属不同线程可从日志线程名/ID 看出。

#### S6 · 空闲探测 + 电源广播

- `idle::idle_ms() -> u64`：`GetLastInputInfo` 取 `lastInput`，`GetTickCount64() - lastInput`。
- `power.rs`：创建一个**隐藏顶层窗口**（`WS_POPUP`、无 `WS_VISIBLE`）接收 `WM_POWERBROADCAST`，收到 `PBT_APMSUSPEND`/`PBT_APMRESUMEAUTOMATIC` 时发 `PowerSuspend`/`PowerResume` 进 channel。
  - ⚠️ 原计划用 message-only 窗口，实测改用隐藏顶层——message-only 窗口**不收广播消息**，`WM_POWERBROADCAST` 收不到。详见 `方案评审记录.md` 一·10。
- ⚠️ 此阶段只**探测并打印**；"flush 时用 idle_ms 判定整段丢弃"的逻辑属阶段二。

**✅ 已验证**：离开键鼠后 `idle_ms` 每 30s 定时采样稳步爬升（30k→60k→90k），动鼠标即清零；真实睡眠/唤醒触发了 `系统挂起`/`系统恢复`，且睡眠期间进程定时器断开（真 suspend）。

#### S7 · MVP 关卡（见 `方案评审记录.md` 一·3）

- 连续运行 **30 分钟**：前台切换、UWP 提取、WASAPI 峰值、idle、电源事件全部正常打印。
- 期间**无崩溃、无 panic**；任务管理器观察 RSS **无明显爬升**（记录 30 分钟后基线值，供阶段五对照）。
- ⚠️ 留意 hook 线程是否在长跑后仍存活（消息循环未死）、COM 句柄是否泄漏（RSS 爬升主嫌疑）。

**✅ 已验证（2026-07-04）**：连续运行 30+ 分钟，前台切换/UWP/WASAPI 峰值/idle/电源全正常；扛过一次真实睡眠/唤醒无崩溃；`tracer.exe`（不含 WebView2）内存 <5MB、无爬升。阶段一收口。

### 风险 & 注意事项

- **hook 线程必须常驻消息循环**，否则回调不再触发；runtime 关停时要能干净摘钩（`UnhookWinEvent`）。
- **COM 生命周期**：WASAPI 探测的线程要 `CoInitializeEx`/`CoUninitialize` 配对。
- **UWP 时序**：子窗口延迟出现是已知坑，别在回调里阻塞等待，宁可丢一次事件。
- **`unsafe` 边界**：每个 Win32 调用都包薄封装 + 单元测试覆盖纯逻辑部分（如路径切分、峰值阈值判定）。

## 阶段二：数据库与存储（纲要）

> ✅ **已完成并验证（2026-07-05）**：P1–P5 全部落地。
> - **模块**：`core/db.rs`（连接/WAL/`schema_version` 迁移/建表）、`core/repo.rs`（`upsert_app` + `add_duration` 小时/天切分 upsert）、`core/config.rs`（config 表 → 内存 `Config`，默认 flush 15min）。
> - **flush 接入 owner**（`owner.rs`）：切换即落库；`FlushTick` 读 idle+audio，`idle≥阈值 && !playing` 整段丢弃、否则 checkpoint 落库；`PowerSuspend` 落库后清段、`PowerResume` 等下次切换。
> - **验证**：7 个单测全过；实测切窗口写库正确（chrome 85s 含一次 60s 整段丢弃）、空闲整段丢弃生效、config 默认/覆盖均正确载入、硬杀进程后 `integrity_check=ok` 且已提交数据全部持久化（丢 ≤ flush 间隔）。

### 落地细节

- `rusqlite` 连接管理：建库时执行 `PRAGMA journal_mode=WAL` / `synchronous=NORMAL` / `foreign_keys=ON`；建 `apps`/`hours_log`/`daily_log`/`categories`/`schema_version`/`config` 表与索引。
- **迁移机制**：`schema_version` 表 + 启动跑未执行迁移（每步事务，幂等）。
- **flush 策略**接入阶段一的 owner task（`Connection` 归属 owner，唯一写者）：
  - 事件：`ForegroundChanged`（切窗口立即写）/ `FlushTick`（周期兜底，默认 15min，可配）/ `PowerSuspend`（写后暂停）/ `PowerResume`。
  - 写入：段时长按本地小时/天切分后 upsert `hours_log`/`daily_log`，累加 `apps.total_time`，单事务。
  - **休眠判定接入**：flush 时读 `idle_ms`，`idle_ms ≥ 阈值` 且 `!is_playing()` → 整段丢弃（评审一·5）。
- **配置**：`config` 表（key-value）+ 启动载入内存 `Config`，owner 热路径读内存；`idle_threshold_ms = flush_interval_secs * 1000`（联动）。

**里程碑**：切窗口与兜底 flush 正确写库；模拟崩溃（kill 进程）后重启，丢失时长 ≤ flush 间隔。

## 阶段三：Tauri 系统整合（纲要）

> ✅ **已完成并验证（2026-07-05）**：托盘/关窗销毁/自启插件全部落地。
> - **托盘**：`TrayIconBuilder` 系统托盘图标 + 右键菜单（显示主窗口 / 退出），左键单击显示/重建主窗口。
> - **关窗销毁 WebView**：点 X 关闭窗口 → 默认关闭行为销毁 WebView2 进程 → `RunEvent::ExitRequested` 触发 `prevent_exit()` 保持后台运行（`AtomicBool` 区分"关窗"与"用户主动退出"）。实测关窗后 `tracer.exe` 工作集从 ~30–50MB 回落到 **<5MB**（debug 模式已近 <10MB 目标）。
> - **自启**：`tauri-plugin-autostart`（`auto-launch` 注册表）插件已注册，`capabilities` 已开放权限。托盘不加开关（放阶段四设置 UI）。Cargo 加 feature `tray-icon`。
> - **已知缺口**：关窗再重建后，WebView 里仍是脚手架模板页（阶段四才替换为真正 UI）。

### 落地细节

- `lib.rs`：`build()` + `run(callback)` 替代 `.run(context)`；`ExitRequested` 时 `prevent_exit()`（配合 `AtomicBool SHOULD_QUIT`）。`show_main_window()` 封装修复已有窗口（`show`/`focus`）或重建（`WebviewWindowBuilder::new`）。
- 托盘菜单仅"显示主窗口"+"退出"；开机自启勾选留给阶段四前端。
- `tauri` dep 加 `tray-icon` feature；`tauri-plugin-autostart = "2"` 已接入。

**✅ 已验证**：托盘退出有效、关窗后 RSS ~4MB（WebView 已销毁）、关窗再开窗口正常。
