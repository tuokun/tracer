## 1. `iconer.rs` GDI 资源清理重复

**文件**：`src-tauri/src/core/iconer.rs`，`save_hicon_as_png` 函数（L52–141）

**问题**：整个函数有 6 个错误早退路径 + 1 个成功路径，每个都手动重复调用 `DeleteObject` / `DeleteDC`。代码冗长且容易遗漏（事实上第 89 行 `SelectObject` 之后如果中间步骤出错，原始位图不会被恢复）。

**修复思路**：引入一个 RAII guard 结构体，在 `Drop` 中自动清理 GDI 句柄：

```rust
struct GdiCleanup {
    dc: Option<HDC>,
    bitmaps: Vec<HBITMAP>,
}

impl Drop for GdiCleanup {
    fn drop(&mut self) {
        for bmp in &self.bitmaps {
            unsafe { let _ = DeleteObject((*bmp).into()); }
        }
        if let Some(dc) = self.dc {
            unsafe { let _ = DeleteDC(dc); }
        }
    }
}
```

然后在 `save_hicon_as_png` 中：
1. 创建 `let mut cleanup = GdiCleanup { dc: None, bitmaps: vec![] };`
2. 每次拿到新句柄时 `cleanup.bitmaps.push(bmp)` 或 `cleanup.dc = Some(dc)`
3. 删除所有手动 `DeleteObject` / `DeleteDC` 调用
4. 唯一不变的是：成功路径末尾需要**主动** drop cleanup 然后 `Ok(())`；错误路径直接 `return Err(...)`，guard 自动析构

## 2. `get_app_icon` 缺少内存缓存

**文件**：`src-tauri/src/lib.rs`，`get_app_icon` 命令（L151–161）

**问题**：每次调用都从磁盘读取 PNG 并重新 base64 编码。前端虽然用 `rankIcons` Map 做了一次去重，但每次打开仪表盘仍需重新走文件 IO + 编码。图标一旦提取就不会变，完全可以缓存。

**修复思路**：在 `IconDir` 结构体中加一个 `Mutex<HashMap<String, String>>` 缓存：

```rust
struct IconDir {
    path: std::path::PathBuf,
    cache: Mutex<HashMap<String, String>>, // process_name → "data:image/png;base64,…"
}
```

`get_app_icon` 逻辑改为：
1. 先检查 `state.cache.lock()` 中是否已有该 `process_name` 的条目 → 命中则直接返回
2. 未命中 → 调用 `core::iconer::extract` → 读文件 → base64 编码 → 写入缓存 → 返回

> 注意：`iconer::extract` 内部已有磁盘缓存（`{stem}.png` 已存在则跳过提取），这里加的是**编码后 data URI** 的内存缓存，省掉的是读文件和 base64 编码的开销。

## 3. `apply_category_rules` 全量读入内存

**文件**：`src-tauri/src/core/repo.rs`，`apply_category_rules` 函数（L483–517）

**问题**：`stmt.query_map(...).filter_map(...).collect()` 把整张 `apps` 表读入 `Vec` 再遍历。个人时间追踪场景数据量不大（几千行），不会造成实际性能问题，但流式迭代更符合 Rust 惯用风格。

**修复思路**：去掉 `collect()`，直接在 `query_map` 返回的迭代器上做 `for` 循环：

```rust
// 改前：
let apps: Vec<...> = stmt.query_map([], |r| ...)?.filter_map(|r| r.ok()).collect();
for (app_id, pname, dname, cat_id) in &apps { ... }

// 改后：
let rows = stmt.query_map([], |r| Ok((r.get(0)?, r.get(1)?, r.get(2)?, r.get::<_, i64>(3)?)))?;
for row in rows {
    let (app_id, pname, dname, cat_id) = match row {
        Ok(r) => r,
        Err(e) => { tracing::warn!("读取 app 行失败: {e}"); continue; }
    };
    if cat_id > 0 { continue; }
    // ... 后续匹配逻辑不变
}
```

注意 `updated` 计数器保留即可。

## 4. Chart ECharts 配置跨页面重复

**涉及文件**：
- `src/routes/+page.svelte` — `buildHeatOption`（L78）、`buildRingOption`（L105）
- `src/routes/stats/+page.svelte` — `buildBarOption`（L80）、`buildRadarOption`（L98）、`buildPieOption`（L117）

**问题**：5 个 ECharts option 构建函数内联在页面组件中，逻辑重复（颜色映射、tooltip formatter、graphic 文本等），且颜色调色板和 `formatDuration` 等工具需重复引用。

**修复思路**：新建 `src/lib/charts/options.ts`，将 5 个函数抽进去，页面只传数据：

```
src/lib/charts/options.ts
├── buildHeatOption(data: number[]): Record<string, unknown>
├── buildRingOption(items: AppRankItem[]): Record<string, unknown>
├── buildBarOption(data: [string, number[]][]): Record<string, unknown>
├── buildRadarOption(points: RadarPoint[]): Record<string, unknown>
└── buildPieOption(slices: PieSlice[]): Record<string, unknown>
```

注意事项：
- `formatDuration` 从 `$lib/utils/time.ts` 引用（已就绪）
- 颜色调色板从 `$lib/utils/colors.ts` 引用 `CATEGORY_COLORS`（已就绪）
- 类型 `AppRankItem` / `RadarPoint` / `PieSlice` 从 `$lib/api/types.ts` 引用
- 函数签名改为纯数据 → option 映射，不依赖 Svelte runtime

改完后，两个页面的 `<script>` 中删除对应的 `buildXxxOption` 函数定义，改为 `import { buildXxxOption } from '$lib/charts/options';`

## 5. 页面组件未消费 Tailwind 设计令牌

**涉及文件**：全部 `src/routes/**/+page.svelte` 和 `src/app.css`

**问题**：`tailwind.config.js` 已定义完整的颜色/字体/阴影令牌（`primary`、`text.primary`、`border`、`boxShadow.card` 等），但页面 CSS 全部使用硬编码 hex 值（`#1A1A32`、`#E0DCF0`、`#9A92C8` 等）。改品牌色需要全局搜索替换 20+ 处硬编码，设计系统形同虚设。

**修复思路**：分两步走，从基础设施到组件逐步替换。

**第一步 — `app.css` 全局类用 Tailwind**：把 `.card` 改为 `@apply` 令牌：

```css
.card {
  @apply bg-surface border border-border rounded shadow-card;
}
```

**第二步 — 组件 CSS 逐步替换**：全局搜索替换最常见的硬编码值。实际涉及的 3 个核心色：

| 硬编码 | 对应 Tailwind 令牌 | 含义 |
|--------|-------------------|------|
| `#1A1A32` | `text-primary` | 主文本色 |
| `#6A62A0` | `text-secondary` | 次文本色 |
| `#9A92C8` | `text-tertiary` | 辅助文本色 |
| `#E0DCF0` | `border` | 边框色 |
| `#F8F6FE` | `sidebar` | 侧栏背景 |
| `#F0ECF8` | `heatmap-bg` | 热力图背景 |
| `#5048E5` | `primary` | 主品牌色 |

将组件 `<style>` 中的 `color: #1A1A32` 改为 `color: theme('colors.text.primary')` 或 CSS 变量。`@apply` 在 `<style>` 中也可用。

> 这一步改动面广、单次修改琐碎但无逻辑风险，适合分批提交。

## 6. `loadRankIcons()` 缺少 `await`

**文件**：`src/routes/+page.svelte`，`loadData` 函数（L39–52）

**问题**：

```typescript
[rank, heatData] = await Promise.all([...]);
loadRankIcons();  // ← 没 await，fire-and-forget
```

当前仅 `onMount` 中调用一次，所以不会出问题。但如果将来加了"刷新"按钮或以其他方式重复调用 `loadData()`，前一次的 `loadRankIcons` 回调可能持有旧的 `rank` 引用，导致将过期图标写入当前的 `rankIcons` Map。

**修复思路**：加一个 `await`——让图标加载在 `loadData` 返回前完成：

```typescript
await loadRankIcons();
```

> 一行改动，消除潜在竞态窗口。
