# 方案评审记录

> 本文件汇总 Tracer 方案评审过程中的所有决策：**技术方案定稿**与**功能取舍**。
> 主方案 `重构方案.md` / `项目基本信息.md` 已据此同步。
> 评审原则：默认对齐 Tai 原版行为，偏离需论证。

## 一、技术方案决策

### 1. session 语义 / flush / 存储模型

**结论：跟 Tai 走聚合路线。**

- **段边界**：同一应用连续在前台 = 一段；窗口切换 / 应用退出 / 系统休眠（`PBT_APMSUSPEND`）/ 空闲判定休眠（鼠标不动 + 无音频播放）任一发生时结束。
- **flush 策略**：事件驱动（窗口切换时立刻写库）+ **15 分钟兜底**（间隔开放为用户可配置项）；崩溃最多丢 15 分钟。兜底 flush 落库后须重置内存的 `_startTime` 与 `_appDuration`，避免下次重复累加。
- **存储模型**：对齐 Tai，仅：
  - `apps`（追加 `total_time` 累计字段）
  - `hours_log`（按小时桶：`data_time` + `app_id` + `time`）
  - `daily_log`（按天桶：`date` + `app_id` + `time`）
  - **不存明细 `app_logs`，不引入 `session_id`**。
- **SQLite 调优**：`journal_mode=WAL` + `synchronous=NORMAL`；flush 由计时 owner task 处理、DB 写在 task 内同步完成，不占用窗口监听（hook）线程（见一·6）。

> **否决的方案**：曾建议"明细 `app_logs` + `session_id` + `app_daily` 预聚合表"。查 Tai 源码（`Data.UpdateAppDuration`）发现其只存聚合表、不存明细，数据量天然极小；v1 亦无明细查询需求，故该方案被否决，改为对齐 Tai。细粒度时段能力推迟到 v2（见二·2）。

### 2. 内存指标

**结论：放宽原方案的 `<5MB`。**

| 项 | 值 |
|----|----|
| 目标（对外宣传） | < 10MB |
| 可接受上限 | < 50MB（仍远低于 Electron 的 100–200MB，轻量定位成立） |
| 红线 | 不设 |
| 验收 | 阶段六：托盘常驻、无 UI 10 分钟后测 RSS 记录基线；显著高于目标（如 >20MB）再定位（缓冲未释放、tokio worker 栈等） |

### 3. 阶段一 MVP 验证

**结论：阶段一内置 30 分钟稳定运行验证关卡。**

阶段一全是 `windows` crate 的 `unsafe` COM/Win32 调用，坑最深。要求先达到 MVP 再展开：能稳定运行 30 分钟并打印当前活动窗口进程名（含 UWP 真实进程提取）、WASAPI 音频峰值、无崩溃、无明显内存增长。

### 4. 缺失项补充

- **测试策略**：休眠判定、时段聚合、窗口/UWP 进程解析等纯逻辑配 Rust 单元测试。
- **图标提取**：`apps.icon_path` 用 `SHGetFileInfo` / `ExtractIconEx` 提取并转 PNG 缓存。
- ~~端口冲突 fallback~~：随网页统计推迟，移出 v1。
- ~~Win10 降级路径~~：仅支持 Win11，不需要。

### 5. 休眠判定细化

**结论：`GetLastInputInfo` + flush 时判定 + 整段丢弃 + WASAPI 豁免；idle 阈值与 flush 间隔联动。**

- **检测 API**：弃用原方案的“`GetCursorPos` 每 5 秒轮询比坐标”，改用 `GetLastInputInfo`（系统级最后输入时刻，鼠标+键盘全计、无状态、无分配），在每次 flush 时读取一次，**零高频轮询**，契合 CPU≈0 目标。属“更优方案”，按“除非不合理/有更优方案才偏离 Tai”原则偏离。
- **裁剪语义**：曾建议按 `idle_ms` 精确裁剪段尾（可免费保住段内真实使用、严格更优）。**用户评估后选择「整段丢弃」**——flush 时 `idle_ms ≥ 阈值` 且无音频，则当前段整段不写。代价：用户在段内最后才离开时，段内真实使用会被一并丢弃。用户明确接受此粗度。
- **阈值联动**：idle 阈值 = flush 间隔（同一可配置值，默认 15 分钟）。少一个旋钮；副作用是 flush 调短→离开判定更激进，调长→更宽松。
- **音频豁免**：保留 WASAPI `IAudioMeterInformation.GetPeakValue()`，有音频播放时跳过整段丢弃，避免看视频/听歌误判。

### 6. 计时与写入线程模型

**结论：单 owner task + mpsc channel，跨线程零共享可变状态、无锁。**

- 一个 Tokio task 独占所有计时状态（`_startTime`/`_appDuration`/`current_app`）与 DB 连接；Win32 hook 线程（跑 `GetMessage` 消息循环）仅解析窗口信息，把事件（`ForegroundChanged`/`FlushTick`/`PowerSuspend`/`PowerResume`）投递进 mpsc channel。
- 唯一写者 → 兜底 flush 与窗口切换事件天然排队、无竞态、无锁；DB 写在 task 内同步执行（WAL 下微秒级，无需额外 writer task）。

### 7. 分类规则设计

**结论：首次入库缓存求值 / glob 语法 / 三字段匹配 / 手动优先 / 从空开始。**

- **求值时机**：app 首次入库跑一次规则、结果缓存进 `apps.category_id`；之后计时/切换不再跑规则。仅当用户编辑规则时，对“未手动指派”的 app 重跑一次（历史 app 补分类靠此）。规避高频正则/ReDoS。
- **语法**：glob 通配符（`*`/`?`），非正则——零学习成本、无 ReDoS。
- **匹配字段**：`executable_path` + `process_name` + `display_name` 三字段皆可（路径信息量最大）。
- **优先级**：手动指派 > 自动规则；手动设定的永不被规则覆盖。
- **默认集**：**不预置**，从空开始。新用户首批 app 入库时无规则→全落“未分类”，靠后续建规则保存时重跑补齐。

### 8. 前端数据通路

**结论：Tauri 专用 invoke 命令 + SQL 下推聚合 + 全量拉/事件重拉。**

- **命令粒度**：专用（`get_today_summary`/`get_app_rank`/`get_hourly_heatmap`…），类型清晰、好测；v1 图表少，命令数可控。
- **聚合位置**：SQL `GROUP BY`+`SUM` 下推到 SQLite（C 引擎直接在存储页聚合、只回聚合后几行），Rust 仅透传+类型映射。Rust 仅在 SQL 表达不了的逻辑时才用（v1 无此需求）。
- **更新方式**：UI 打开/切日期时一次性全量拉当前视图；后台写库后 `app.emit("data-updated")` 通知前端重拉当前视图。不搞增量 diff。

### 9. 配置 / 迁移 / 保留

**结论：配置 = SQLite `config` 表 + 内存缓存；迁移 = 手写 `schema_version` 表；数据永久保留。**

- **配置存储**：存进同一 SQLite 库的 `config`（key-value）表，启动载入内存 struct、热路径读内存（介质不影响热路径性能）、变更时刷新。复用同一套 DB/备份/迁移，零额外文件依赖，天然归属后端（满足“大部分时间只有后台进程”）。
- **Schema 迁移**：`schema_version` 表记录版本，启动依次跑未执行的迁移脚本（每步包事务）。rusqlite 无 EF 式自动迁移，故手写。
- **数据保留**：`hours_log`/`daily_log` 永久保留、不主动清理（一年几千~几万行，SQLite 体积/查询均无压力）。

### 10. 电源监听窗口：隐藏顶层 vs message-only

**结论：用隐藏顶层窗口（`WS_POPUP` + 无 `WS_VISIBLE`，父窗口为 `None`），而非 message-only。**

- 原计划（`实现计划.md` 阶段一 S6 初稿）写的是 message-only 窗口收 `WM_POWERBROADCAST`。
- **实测发现**：按 Win32 规范，**message-only 窗口不接收广播消息**（`HWND_BROADCAST` 不枚举它们），`WM_POWERBROADCAST` 会收不到 → 挂起/唤醒事件丢失。
- **改法**：创建隐藏的顶层窗口（`WS_POPUP`、不加 `WS_VISIBLE`、父窗口传 `None`），既能可靠收广播，又不可见、不干扰用户。
- **验证**：阶段一 S7 真实睡眠/唤醒测试，`PowerSuspend`/`PowerResume` 正确触发（睡眠期间进程定时器断开，确认真 suspend）。
- 属"更优/必要方案"偏离（message-only 在此场景不合理），符合"除非不合理/有更优方案才偏离"原则。

## 二、功能取舍

### 1. 浏览器网页统计 — 推迟到 v2

**功能**
来自 `重构方案.md` 第三章第 2 节"网页浏览监测"。Rust 起本地 WebSocket（`127.0.0.1:8908`）接收浏览器扩展推送的网页活跃数据（`url`/`title`/`duration`），解析域名后存入 `web_sites`/`web_logs`，在 Dashboard 展示"网站浏览分布"。目的是补齐桌面侧看不到的网页维度（桌面侧只能统计到 `chrome.exe` 进程级）。

**决策**：推迟到 v2，v1 不实现。

**依据**
- 收益有限：仅增加"域名级"增量维度；浏览器进程级时长 v1 桌面侧窗口监听本就能统计，核心闭环不依赖此功能。
- 成本不成比例：
  1. 鉴权无完美方案——本地 ws 存在 CSWSH 风险，可落地的 Origin 白名单 + secret 仅"够用"，最强方案 Native Messaging 对本应用过重。
  2. 要开发并维护浏览器扩展（Chrome/Edge/Firefox）+ 上架过审核。
  3. 用户需手动装扩展，与"极简后台"定位冲突。
  4. 引入端口冲突、session 语义、`web_sites`/`web_logs`/预聚合整套数据层复杂度。
  5. MV3 service worker 等政策变化的长期维护负担。

**对主方案的影响**
| 位置 | 处理 |
|------|------|
| `重构方案.md` 第三章第 2 节 | 标注 `v2` |
| `重构方案.md` 路线图阶段三 | 标注 `v2` / 移出 v1 路线 |
| `重构方案.md` Schema `web_sites`/`web_logs` | 标注 `v2`，v1 不建表 |
| `重构方案.md` 前端"网站浏览分布"图表 | 标注 `v2` |
| `项目基本信息.md` 路线图 | 6 阶段 → v1 为 5 阶段 |

**后续（重启前待拍板）**
1. **鉴权方案**：威胁为 CSWSH（任意网页可连 `ws://127.0.0.1:8908` 污染数据）。候选——A. Origin 白名单 + 扩展硬编码 secret（**推荐**，双层防御、不引入 Native Messaging）；B. 仅 Origin 白名单；C. Origin + Native Messaging 发 token（最强但过重）；D. 暂不鉴权仅记录来源。
2. **token 分发**：MV3 扩展无法直读本地文件，需定 token 到达扩展的机制（Native Messaging / 硬编码 / 其他）。
3. `web_logs` session 语义 + 是否引入 `web_daily` 预聚合。
4. 扩展分发策略与覆盖浏览器范围。
5. 端口冲突 fallback 与扩展发现机制。

### 2. 精确时段统计（细粒度时间桶）— 推迟到 v2

**功能**
讨论 `app_logs` 存储粒度时浮现的能力：比 Tai 的"小时桶"更细的时间维度统计，如 15 分钟桶、分钟桶，或精确到每次窗口切换的时间轴回放（能回答"今天 14:10–14:25 用了 Chrome"）。

**决策**：推迟到 v2，v1 直接按 Tai 的小时桶聚合。

**依据**
- v1 Dashboard 为"24 小时热力图 + app 排行"，小时桶刚好满足，存储最小（一年几千行级别）。
- 用户当前能接受"某时段内多 app 共存累计、不要求时序"的形式，小时桶已满足。
- 细化桶 / 加明细表属增量能力，无明确 UI 驱动前不引入。

**对主方案的影响**
- v1 Schema 直接对齐 Tai：`hours_log`（小时桶）+ `daily_log`（天桶）+ `apps.total_time`。
- v1 不建明细 `app_logs`、不引入 `session_id`。

**后续（重启前待定）**
1. 桶粒度选型：15 分钟桶 / 分钟桶 / 明细表（数据量与查询能力递增）。
2. UI 驱动确认：是否有"时段下钻"或"时间轴回放"需求，决定桶要多细。
3. 若选明细表：需评估与聚合表的双写一致性、迁移路径。

### 3. 平台支持范围 — 仅 Win11，放弃 Win10

**功能**
原方案未限定 OS 版本，UI 计划使用 Mica/Acrylic 毛玻璃材质，理论上需为 Win10 准备降级路径。

**决策**：仅支持 Windows 11，不考虑 Win10（明确放弃，非推迟）。

**依据**
- 收窄平台省去 Win10 的 Mica 降级与部分 API 兼容适配，聚焦核心功能与性能目标。
- Win11 已是主流装机，放弃 Win10 对目标用户群影响可控。

**对主方案的影响**
- `重构方案.md` 前端 UI 章节：Mica/Acrylic 直接用，无需 Win10 降级。
- `项目基本信息.md`：已标注"目标平台：仅 Windows 11"。

**后续**：无。若未来评估需回填 Win10 支持，再单独立项。
